# Signal System

> Proactive customer-success automation, triggered by typed backend events — never inferred chat
> intent. It analyzes health / usage / renewal / NPS / sentiment signals and, after compliance
> review, proactively drafts outreach or notifies the CSM.

## 1. Positioning

- One of the two top-level systems (alongside conversation), sharing the same runtime
  (`BaseOrchestrator`) but with disjoint specialist sets.
- `SignalOrchestrator.supports_external_writes = True` — it can send email / notify the CSM, so
  compliance review is always on (`skip_critic_for_simple=False`).
- Temporal workflows own durable orchestration (retries, dedupe, status), replacing the early
  Redis-polling worker.

## 2. Triggers (4 sources)

| Source | Entry | Notes |
|---|---|---|
| Dashboard scan | `POST /signals/scan` → `TenantSignalScanWorkflow` | runs all detectors; each signal fans out a `ProcessSignalWorkflow` |
| Manual | `POST /signals` | explicit payload |
| Conversation → signal bridge | conversation `_apply_loop_side_effects` | complaint / escalation / high-urgency → `negative_sentiment` (escalation → `nps_detractor`) |
| NPS detractor | `POST /nps/surveys/{id}/response` | score 0-6 → `nps_detractor` |

## 3. Detectors

`apps/agent_service/src/signals/detectors.py` — pure SQL scans over `customers` /
`customer_profiles` (degrade to empty on DB failure):

| Detector | Signal type | Default threshold |
|---|---|---|
| renewal risk | `renewal_risk` | `renewal_date` within N days (60) |
| low health | `low_health` | `health_score` < 50 |
| usage decline | `usage_decline` | active users drop > 30% |
| composite risk | `renewal_usage_risk` (critical) | usage decline + imminent renewal |
| ticket spike | `support_ticket_spike` | recent tickets ≥ 5 |
| negative sentiment | `negative_sentiment` | profile has `risk_signals` / negative `last_sentiment` |

## 4. Orchestration (Temporal + P-E-R)

### 4.1 Temporal workflows (`apps/temporal_worker/src/workflows.py`)

- `ProcessSignalWorkflow`: record → processing → process → done/failed (auto-retry transient failures).
- `TenantSignalScanWorkflow`: run detectors → one child workflow per signal (deterministic id + reject-duplicate).

### 4.2 SignalOrchestrator (P-E-R)

`apps/agent_service/src/agent/signal/signal_orchestrator.py` (subclass of `BaseOrchestrator`):

1. **Planner** (`signal_planner.py::build_signal_plan`): deterministic
   `health_analysis → playbook_retrieval → outreach_draft` chain.
2. **Executor**: dependency-aware parallel subagents.
3. **Reflector**: `ComplianceCriticAgent` (always on for the signal path).
4. **on_approved**: persist profile → release compliance-approved external writes via the tool-gateway MCP.

### 4.3 Signal specialists

| Role | Domain | Allowed tools |
|---|---|---|
| `HealthAnalysisAgent` | signal | query_health |
| `PlaybookRetrievalAgent` | shared | query_playbooks |
| `OutreachDraftAgent` | signal | (none — drafts only) |
| `NpsOutreachAgent` | signal | query_health, query_nps_history, create_nps_survey, calculate_tenant_nps |
| `QbrReportAgent` | signal/reporting | query_tenant_portfolio, query_tenant_nps, query_renewal_pipeline, query_signal_summary |

## 5. Feature modules

### 5.1 NPS

- **Survey dispatch**: `NpsCampaignWorkflow` → `select_nps_candidates` → `create_and_send_survey`
  (create survey + send the invite through the gated `send_email` path; marked `sent` only on success).
- **Score submission** via `POST /nps/surveys/{id}/response` only (never an LLM).
- **Deterministic classification**: promoter 9-10 / passive 7-8 / detractor 0-6.
- **Detractor**: score 0-6 → `nps_detractor` signal → notify CSM (never auto-reply the customer).
- **Aggregate NPS** via `calculate_nps` (deterministic, never stored on the customer row).

### 5.2 QBR

- **Trigger**: `POST /qbr/generate` → `GenerateTenantQbrWorkflow` (inline fallback when Temporal is down).
- **Rule**: SQL computes facts, the LLM only writes the narrative (`aggregate_portfolio`).
- **Narrative**: generated by `QbrReportAgent` from the snapshot, compliance-reviewed before persist.
- **Delivery**: `resolve_qbr_recipient` → `deliver_qbr_email` sends the report through the gated
  `send_email` path and marks it delivered (marked `failed` on failure).

### 5.3 Email

- `send_email` is an `MCP_ACTION` tool, executed only through `apps/tool_gateway`.
- **Gating** (`apps/tool_gateway/src/service.py`): approval (`approval_id`) → idempotency
  (`idempotency_key`) → schema → send.
- **Providers** (`apps/tool_gateway/src/email_providers.py`, selected by `EMAIL_PROVIDER`):
  `mock` (no-op, default) / `console` (log) / `google` (real Gmail OAuth, fails closed without credentials).
- **CSM notify** (`packages/tool_system/src/tools/notify_csm.py`): `nps_detractor` emails are
  rewritten to `EMAIL_FROM` (notify CSM only).
- **Shared helper** `apps/temporal_worker/src/email_delivery.py::send_approved_email`: NPS invites
  and QBR delivery reuse the same approval → gateway → provider path.

### 5.4 External-write safety

- Subagents only propose writes (`proposed_external_writes`); `outreach_draft` has
  `DEFAULT_ALLOWED_TOOLS == []` by design.
- Only the `emit_or_execute_approved_payload` sentinel releases writes in `on_approved`; the
  gateway is tenant-authoritative.

## 6. Scheduling

`apps/temporal_worker/src/worker.py` creates Temporal Schedules (env-gated tenant allowlists):

- Scan: `SIGNAL_SCAN_TENANTS` / `SIGNAL_SCAN_INTERVAL_MINUTES` (default 60).
- NPS campaign: `NPS_CAMPAIGN_TENANTS` / `NPS_CAMPAIGN_INTERVAL_DAYS` (default 30).
- QBR: `QBR_TENANTS` / `QBR_INTERVAL_DAYS` (default 90).

## 7. What's lacking

- NPS candidate selection skips recently-surveyed (`NPS_RECENT_SURVEY_DAYS`) and missing-email
  customers; still no richer health/engagement-based policy.
- Limited detector coverage (no churn-prediction model, expansion signals, or finer usage signals).
- `escalate_to_human` / `check_human_availability` / `process_refund` are deterministic prototype
  stubs (see the `TODO(gate)` markers).
- `build_signal_plan` is a deterministic hardcoded chain (no semantic planning / dynamic tool selection).
- No Temporal durable long-waits (e.g. "wait 48h then follow up").
- Detractor loop is notify-CSM only (no auto-recovery outreach or closure metrics).
- Single email channel (Gmail + mock + console) — no SMTP/Outlook, no bounce/unsubscribe/delivery tracking.
- `resolve_qbr_recipient` orders CSM-first; still no multi-CSM routing / per-account ownership.
